# E911 地址登记

设备概览的“原运营商”旁会为美国 SIM 显示“E911 地址”按钮。识别依据是 SIM 的归属网络及运营商品牌，不使用当前漫游网络判断。

## 运营商适配

| 线路 | 登记方式 |
| --- | --- |
| RedPocket GSMA、AT&T 网络的 NSDS 线路 | 在 VoCat 弹窗内完成 SIM 鉴权、地址校验、开通及运营商回读。RedPocket GSMA 已用真实线路验证。其他 AT&T 网络品牌是否可开通由运营商返回结果决定。 |
| T-Mobile 网络：T-Mobile、Metro、Tello、Mint、Ultra、RedPocket GSMT、Google Fi 等 | 新增 MSP v2 候选适配：SIM EAP-AKA 鉴权、VoWiFi entitlement 查询、受支持返回结构中的运营商登记页交接及状态刷新。无这些品牌的实卡，尚不能声称已验证可登记。 |
| Verizon 网络：Verizon、Visible、US Mobile Warp、Xfinity、Spectrum、Tracfone、Total 等 | 同上，使用运营商配置中的主 entitlement 服务。尚未实卡验证；仅有主网络归属不保证品牌、套餐和模块均获准使用。 |
| US Mobile、RedPocket、Boost 等多网络品牌 | 保留品牌名称及账户入口，按当前 SIM 归属网络选择 AT&T NSDS、T-Mobile/Verizon MSP 或标准 TS.43，而非按品牌硬编码宿主网络。 |
| UScellular、C Spire、Cellcom 及其他美国线路 | 新增 GSMA TS.43 EAP relay、标准归属网络服务发现、ap2004 JSON/XML 解析、官方登记页交接及状态查询。依赖运营商提供标准发现服务；尚未实卡验证。 |

第三方品牌优先于宿主网络匹配。例如 US Mobile 的 AT&T 线路仍显示 US Mobile，尝试其归属网络的 SIM 开通流程。新增品牌显示“尚未完成实卡验证”。服务拒绝模块或没有返回受支持的登记页时，显示错误并保留品牌账户入口；不会把账户链接当成已完成自动适配。

### 手机式运营商登记页

1. 后端使用当前 SIM 进行 EAP-AKA，令牌及 Cookie 保存在 15 分钟会话中。
2. 从 VoWiFi 响应中取得 ServiceFlow_URL/ServiceFlow_UserData，限制到对应运营商或品牌的受信 HTTPS 域名。
3. 用户点击“打开运营商E911登记页”，经过有登录保护的交接页面，在新窗口将表单数据提交给运营商。令牌不放入设备 JSON、前端状态或本地数据库。交接页禁止缓存、禁止 Referer、使用单次 CSP nonce；不代理运营商脚本到管理后台同源页面。
4. 用户在运营商页面填写真实地址并同意条款，返回弹窗点击“刷新运营商状态”。不采信网页关闭、回调或 HTTP 200 作为登记成功的证据。
5. TS.43 要求 VoWiFi 已启用、ProvStatus 为已开通或不要求开通、AddrStatus 明确为已登记、TC_Status 为已接受或不要求，并检查可选地址到期时间。状态缺失、过期或只说明地址不需要时，不显示 E911 登记成功。

运营商状态确认不等于回读了具体街道地址，因此页面使用“已确认E911登记状态”区分 AT&T 的地址回读结果。MSP 仅返回通用的 entitlement enabled 时不会显示 E911 成功。MSP 私有服务属性格式、设备认证要求、原生 WebView 回调和 MVNO 特有行为仍可能需要实卡补充适配；新增实现是协议级候选支持，不能据此宣布绝大部分美国线路已可用。

### 实现依据（2026-10-16 核对）

- [GSMA TS.43 v13.0](https://www.gsma.com/get-involved/working-groups/wp-content/uploads/2026/02/TS.43v13.0-Service-Entitlement-Configuration.pdf)：第 2 节标准服务发现、EAP relay、JSON/XML；第 3 节 VoWiFi、ServiceFlow、地址/条款/开通状态。
- [Android IMS service entitlement](https://source.android.com/docs/core/connect/ims-service-entitlement) 和 [AOSP EapAkaApi](https://android.googlesource.com/platform/frameworks/libs/service_entitlement/+/refs/heads/main/java/com/android/libraries/entitlement/eapaka/EapAkaApi.java)：EAP-AKA HTTP 交互及运营商 WebView 流程。
- [Apple 运营商包索引](https://itunes.apple.com/WebObjects/MZStore.woa/wa/com.apple.jingle.appserver.client.MZITunesClientCheck/version?languageCode=en)：已从官方 CDN 包核对 T-Mobile、Ultra/Mint、Verizon、Visible、Verizon MVNO、Xfinity、Spectrum 的 CarrierEntitlements。T-Mobile 主服务为 eas3.msg.t-mobile.com；上述 Verizon 包主服务为 spc.myvzw.com/ium-RoadrunnerInterface/servlet/IUMServlet。spc-pfe 是部分配置中的 secondary overlay，未将所有 MVNO 一概路由到它。
- [OpenBubbles rustpush 原始实现](https://github.com/OpenBubbles/rustpush/blob/master/src/util.rs)：MSP v2 getAuthentication/postChallenge 的 SIM EAP 报文和传输格式参考。它不是运营商 E911 接口文档；未将其视作 E911 端到端兼容证据。

## 弹窗内登记

1. 使用当前 SIM 完成运营商 EAP-AKA 鉴权，读取当前地址和 Wi-Fi Calling 开通状态。
2. 输入真实地址：街道、门牌号、房间号（如有）、城市、州、邮编。
3. 校验地址并选择运营商返回的规范化地址。
4. 阅读并同意运营商返回的 Wi-Fi Calling 条款，然后提交。
5. 读取运营商的地址记录、地址验证状态、条款状态和服务权限。全部确认后才显示成功；如 VoWiFi 已启用，则安排重连。

地址写入返回成功不等同于登记成功。VoCat 还会核对读回的地址是否与本次选中的地址一致。未确认或等待验证时，弹窗允许刷新运营商状态。

会话绑定当前 ICCID，换卡后必须重新打开弹窗。SIM 密钥不离开卡片；AKA 计算结果、运营商令牌、Cookie 和会话凭证不会发送给前端或写入日志。关闭弹窗会释放会话，过期会话不能继续提交。

原有仅保存本地地址的 `/websheets/` 流程已移除。

## API

所有接口使用现有管理员会话和 CSRF 保护：

- `POST /api/devices/{id}/vowifi/e911`：识别运营商并启动登记会话。
- `POST /api/devices/{id}/vowifi/e911/{session}/verify`：校验地址。
- `POST /api/devices/{id}/vowifi/e911/{session}/submit`：提交选中的规范化地址及条款确认。
- `POST /api/devices/{id}/vowifi/e911/{session}/refresh`：查询运营商状态。
- `DELETE /api/devices/{id}/vowifi/e911/{session}`：释放临时凭证。
- `GET /api/devices/{id}/vowifi/e911/{session}/portal`：核对活动 SIM 后，将浏览器交接到运营商登记页；不返回 JSON 凭证。

## IKE COOKIE 重复挑战

网络延迟使 IKE_SA_INIT 请求重发时，网关可能返回重复的 COOKIE。客户端回传第一份后，延迟到达的相同 COOKIE 不应再次计为新挑战。

传输层现在忽略与已回传 COOKIE 相同的重复挑战，继续等待有效响应，仍受总超时限制。不同 COOKIE 可以进行有界重试。SOCKS5 在网关第一次回应时固定目的地址，避免将一个网关的 COOKIE 发给另一个网关。

此修复处理重复报错的原因，并不保证运营商不再主动发起 COOKIE 挑战或网络不再超时。
